# Company Operational Agent Scope

## Problem Statement

Company operations data is spread across telemetry databases, device
inventory, Grafana, alert rules, runbooks, and support channels. Operators
must manually correlate those systems before they can answer basic questions
such as:

* Which devices are currently affected?
* Is an alert supported by authoritative telemetry?
* Has the same failure happened before?
* Which approved runbook should be followed next?

The target is not a generic chatbot with unrestricted database access. It is
one source-aware operational agent that synchronizes approved company systems
behind controlled tools and returns auditable answers.

## Current Demo

The current project demonstrates:

* read-only device and telemetry retrieval
* Company DB and simulator source selection with explicit fallback
* multi-runtime agent comparison
* provisional alert-rule discovery
* web and Telegram interaction channels
* persisted chats and visible execution traces

This is a proof of concept. It does not yet prove production synchronization,
authorization, official rule ownership, or safe operational actions.

## Target Capability

The company agent should:

* answer fleet and device-status questions from authoritative sources
* correlate telemetry, inventory, alerts, and approved runbooks
* identify the active data source and observation time in each answer
* preserve tool calls, evidence, user identity, and decisions in an audit log
* apply role-based access, query allowlists, and rate limits before data access
* draft operational actions while requiring human approval for side effects
* serve the same policy and tool layer across web, Telegram, and future channels

## Non-Goals

The first production version should not:

* execute arbitrary MongoDB queries generated by an LLM
* write to company systems or remediate devices without approval
* present simulator fallback data as company data
* treat discovered or provisional rules as official policy
* become a general company knowledge bot without a defined operational scope

## Reference Architecture

```text
Web / Telegram / API
        |
Agent gateway and conversation state
        |
Identity, RBAC, rate limit, audit
        |
Read-only typed tool contracts
        |
MongoDB / inventory / Grafana / runbooks
```

The LLM chooses among typed tools. A policy proxy validates identity, source,
operation, fields, limits, and query cost before any company system is read.

## Production Exit Criteria

A production pilot is ready when:

* one named operational team and its top tasks are defined
* every answer identifies source and freshness
* company-source disconnection and fallback are visible and tested
* read access follows least privilege and is auditable
* benchmark tasks use frozen reference snapshots and repeatable evaluation
* critical factual errors and unsupported claims stay below an agreed threshold
* a human owner approves official rules, runbooks, and any action workflow

## Recommended First Use Case

Start with read-only incident triage for the IoT operations team:

> Given a device, alert, or fleet question, collect authoritative telemetry and
> inventory evidence, summarize likely impact, and recommend the approved next
> diagnostic step without changing any company system.

This scope is narrow enough to validate trust, synchronization, and access
control before adding broader company workflows.
